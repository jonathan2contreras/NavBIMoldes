# Base44 dev notes — NaBiMoldes

- Stack: FastAPI backend (`backend/server.py`, port 8001) + CRA/craco React frontend (port 3000) + MongoDB. Run with `docker compose -f docker-compose.base44.yml up -d`.
- Wiring is separate-origin: the frontend calls `REACT_APP_BACKEND_URL=https://8001-$BASE44_PUBLIC_HOST_SUFFIX`. CORS is `*`; there are no login tokens or session cookies.
- Backend install skips `emergentintegrations` and `litellm` from requirements.txt (private Emergent index, not imported by the code). Deps live in the `backend-venv` volume; first boot takes ~2 min.
- `backend/static/nab3d.glb` (~58MB) is loaded at startup; "Loaded 12275 objects" in backend logs means startup is OK.
- Object storage (photo/PDF uploads) needs a valid `EMERGENT_LLM_KEY`. When it is unset the backend logs a WARNING at startup ("Object storage not configured") instead of an error and keeps running; uploads are the only feature affected.
- Login: shared password (`ADMIN_PASSWORD`, plain env secret) → `POST /api/auth/login` returns a 30-day JWT (`JWT_SECRET`), kept in localStorage (`nabimoldes_admin_token`) and sent as `Authorization: Bearer`. `backend/auth.py` middleware rejects every non-GET `/api/*` request without a valid token (401), except `PUBLIC_WRITES` (login, the three PDF-export POSTs, and the viewer's `/api/facades` + `/api/dims` caches). New write endpoints are protected automatically; add read-only POSTs to `PUBLIC_WRITES`. The middleware is registered before CORS so 401s keep CORS headers. Frontend: `RoleContext` (`isAdmin`, `login`, `logout`), `AdminLogin.jsx` button in the nav; the Moldes tab and «Restaurar» are admin-only. `/login` still redirects home.
- `@emergentbase/visual-edits` is optional in craco.config.js; webpack "Compilation.assets" deprecation warnings are harmless.
- PWA: `frontend/public/manifest.json` + `frontend/public/icons/` (generados con Pillow) + `frontend/public/sw.js`. El service worker se registra SOLO en `NODE_ENV=production` (`frontend/src/index.js`) para no servir versiones cacheadas en el preview. El layout raíz usa `h-dvh` (no `h-screen`) por la barra del navegador móvil.
- Fabrication phases (`backend/scheduling/phases.py`, Mongo `fabrication_phases`): fronts + Monday-based weeks, items kept in selection order. Phase weeks are ON-SITE INSTALLATION weeks; the schedule is FABRICATION. When the list is non-empty the scheduler fabricates only listed panels from the schedule start date, ordered by installation week then list order (no week window constraint); `phase_late` counts panels fabricated on/after their installation Monday. Panel m² = **mitad de la superficie total de la malla** (`mesh_surface_area(name) / 2` en `server.py`, cacheado en `AREA_CACHE`), es decir se suman las áreas de todos los parches del panel (piel, nervios y cantos) y se divide entre 2. Es una **aproximación pendiente de validar** contra el «área de superficie del sólido» de Revit: para los 533 paneles de fachada da 6.565,97 m² frente a los 6.132,20 m² de Revit (+7,1 %). Si el panel no tiene malla en el GLB cae al bounding box `dims[1] * max(dims[0], dims[2])` de `dims.json` (Y es alto). Ojo: las piezas del GLB **no son sólidos cerrados**, son conjuntos de parches sueltos (124–263 por panel), por eso no se puede reproducir exactamente el área de Revit desde la malla.
- Installation timeline: `/installation` edits existing front/week groups via `PATCH /api/phases/week` (admin login required). Dates normalize to Monday (UI shows Monday–Saturday); occupied destinations in the same front return 409. Atomic array updates preserve list order and other fronts; production schedule documents are not modified. Gantt labels and model week legends use the viewer's separate `highlightWeek` command (blue highlight, all geometry stays visible), not bulk-selection state.
- Installation regressions: `docker compose -f docker-compose.base44.yml exec -T backend /venv/bin/python -m pytest tests/test_phase_weeks.py -q` (six tests; temporary Mongo collections removed afterward).
- Login regression tests: `docker compose -f docker-compose.base44.yml exec -T backend /venv/bin/python -m pytest tests/test_login_free.py -q` (needs `ADMIN_PASSWORD` + `JWT_SECRET` in the container). Older integration tests assume the removed `/api/admin/verify` endpoint and need updating before a full-suite run.
- Despliegue (fuera de Base44): frontend en Netlify (`netlify.toml`, base `frontend`, `yarn build` → `build`, redirect SPA, `CI=false`); backend en Render (`render.yaml` → blueprint con `rootDir: backend` y `backend/Dockerfile`, health check `/api/`). Render no ofrece MongoDB: se usa un clúster de MongoDB Atlas y su cadena va en `MONGO_URL` (`sync: false`, se pega al crear el blueprint). Al desplegar el frontend hay que definir `REACT_APP_BACKEND_URL` en Netlify con la URL de Render (se incrusta en build time). `APP_NAME = "bimtracker"` en `server.py` y `DB_NAME` conservan el nombre viejo a propósito: cambiarlos apuntaría a otro espacio de almacenamiento / otra base de datos.
- Despliegue VPS (alternativa preferida por el usuario): `deploy/docker-compose.prod.yml` + `deploy/Caddyfile` + `deploy/.env` (desde `deploy/.env.example`; `.gitignore` tiene `!deploy/.env.example`). Origen único: Caddy enruta `/api/*` → backend:8001 y el resto → nginx del frontend (`frontend/Dockerfile` + `frontend/nginx.conf`, fallback SPA, `sw.js`/`manifest.json` sin caché). `REACT_APP_BACKEND_URL=https://$DOMAIN` es build arg: cambiar DOMAIN requiere rebuild. Reutiliza `backend/Dockerfile` (el de Render; `PORT` por defecto 8001). Solo Mongo necesita volumen (el GLB va en la imagen; las subidas van a Emergent). Verificado en el sandbox con `DOMAIN=localhost` (cert interno de Caddy): `up -d --build` con `--env-file /tmp/prod.env`, luego `down -v`. Auto-deploy: `.github/workflows/deploy.yml` (push a `main` + manual) hace SSH al VPS, `git reset --hard <sha>` y `sh deploy/update.sh` (build + espera backend `healthy`, falla a los 5 min). Secrets de GitHub Actions (no de Base44): `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_PATH`, opcionales `VPS_PORT`, `VPS_KNOWN_HOSTS`.
- Plazos de moldes: `MoldProductionTimeline.jsx` muestra hitos horizontales con desplazamiento (separación uniforme, no a escala), agrupados por primer día de producción. `MoldReadinessPage` alterna esta vista inicial y el Gantt con el botón «Ver cronograma» / «Ver línea de tiempo»; solo una vista se monta a la vez. Los moldes con `copies > 1` se marcan con «N copias» en la línea de tiempo, en el Gantt de plazos (`MoldReadinessTimeline.jsx`) y en el PDF (tabla «M-04 (2 copias)» + «(+N copias)» en la cabecera); no se crean hitos adicionales, pero el contador «Inicio de producción / N moldes» sí suma cada copia como un molde (5 moldes con una copia doble = 6). El PDF conserva las tablas verticales y añade la línea de tiempo completa en una única hoja A4 horizontal (`backend/scheduling/readiness_timeline_pdf.py`, ajuste vectorial sin recortes). Pruebas PDF: `docker compose -f docker-compose.base44.yml exec -T backend /venv/bin/python -m pytest tests/test_readiness_timeline_pdf.py -q`. Reutiliza `buildReadiness`; el fin es `start + total - 1`. Pruebas: `docker compose -f docker-compose.base44.yml exec -T frontend sh -c 'CI=true yarn test --watch=false --runInBand --transformIgnorePatterns "node_modules/(?!date-fns/)" --runTestsByPath src/components/schedule/MoldProductionTimeline.test.jsx'` (CRA/Jest necesita transformar los módulos ESM de date-fns).
- Gantt PDF (`GET /api/schedule/export-gantt.pdf?layout=pages|single`, `backend/scheduling/export.py`): `pages` (defecto) = una hoja A4 apaisada por bloque de 14 días; `single` = una sola hoja ancha con todos los días (ancho de columna igual, limitado a 200 in de página). `ScheduleExport.jsx` pregunta el formato en un diálogo. Duplicar moldes = botón «Duplicar (N)» en cada fila del Gantt por molde (admin), `PATCH /api/schedule/mold-copies`, recalcula todo.
- Exportaciones PDF de reportes: `backend/scheduling/report_exports.py` monta `POST /api/reports/mold-readiness.pdf` y `POST /api/reports/analysis.pdf`. El frontend ya calcula ambas vistas (`components/schedule/moldReadiness.js`, `lib/scheduleAnalysis.js`) y envía las filas resueltas; el backend solo maqueta con reportlab. Así el PDF coincide siempre con la pantalla y la lógica de plazos/análisis no se duplica en Python. Los botones son `components/schedule/ReadinessExport.jsx` y `components/progress/AnalysisExport.jsx`.
